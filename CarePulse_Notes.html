Session 1 — Project Selection & Phase 0 Foundations

Sep 2026

Decision Which project, and why it targets this specific job

Combined two independent project proposals (an AWS/Snowflake healthcare pipeline, and a CMS-Medicare anomaly-detection idea) into one plan, explicitly shaped around a real job posting: Software Engineer III — ETL/PySpark | AWS | Snowflake | Python | SQL.

Why this matters for interviews: researched actual postings for this title before designing anything. They consistently asked for AWS Glue (PySpark), Terraform (IaC), SageMaker integration, S3/Athena/Redshift, CI/CD, and Glue job performance tuning. The project was designed backwards from those requirements — not a generic tutorial project retrofitted with a job title.

Decision Synthea over CMS Medicare data

Originally proposed CMS Medicare Part D Prescriber data (real claims, provider-level). Reversed this in favor of Synthea synthetic patient data.

RequirementCMS Part DSynthea
Supervised ML with a real label❌ no patients/timeline, aggregate only✅ patient encounters over time → real 30-day readmission label
Control data volume for PySpark❌ fixed ~25M rows✅ generate any patient count
PHI-free, publishable✅✅ (fully synthetic)
Why: the stated goal was to learn ML properly. Unsupervised anomaly detection (the CMS idea) has no ground truth to validate against. Supervised learning with leakage/imbalance/splitting concerns teaches far more of the ML fundamentals actually tested in interviews.

Honest caveat to state in interviews: a model performing well on Synthea has not been clinically validated — Synthea's patients follow rule-based disease modules, so learned patterns partly reflect the generator, not medicine. This project is an educational demonstration, not clinical decision support. Saying this unprompted is a maturity signal.

Interview Question

Why did you choose synthetic data instead of a real public healthcare dataset?

Real patient-level data triggers HIPAA/PHI concerns and can't be freely published in a portfolio. Synthea generates realistic-but-fake patient histories — encounters, conditions, meds, procedures — with zero access friction, so I could build a genuine supervised-learning pipeline (readmission prediction) without any of the legal risk, while being upfront that results are an educational demonstration, not clinically validated.

Decision Sizing the Synthea generation — reasoned, not guessed

Ran a 100-patient test first (produced 112 records incl. deceased). Measured real output: 85 MB total, and checked the ENCOUNTERCLASS distribution before picking a population size:

ClassCount (of 7,596)
ambulatory4,562
wellness1,434
outpatient930
emergency269
urgentcare257
inpatient61

Only inpatient/emergency encounters qualify for the 30-day readmission label — just 4.3% of all encounters. Reasoned that population size must be driven by qualifying-encounter volume, not total GB, since positive labels will be a small fraction of that already-small pool.

Disk constraint hit mid-plan: initial estimate for 50,000 patients was ~38 GB (naive linear scaling), but only 21.77 GB was free on disk. Fixed two ways: (1) discovered exporter.csv.excluded_files in synthea.properties and dropped unused exports (claims_transactions.csv alone was 63% of total size and isn't needed for the readmission model) — cut the per-patient footprint by ~73%; (2) separately freed 19 GB of disk by uninstalling unused tools (Anaconda, Katalon, Codex, stale caches). Final run: 57,538 patients, ~12 GB, comfortably within budget.

Error / Gotcha Synthea doesn't delete excluded files from previous runs

After adding exporter.csv.excluded_files and re-running, the excluded files (claims.csv, claims_transactions.csv, etc.) were still present in the output folder — timestamps revealed they were stale leftovers from the first run, not newly written.

Root cause: Synthea's CSV exporter only writes files for enabled exports; it never proactively deletes files that become excluded between runs. Fix: always Remove-Item -Recurse -Force output before every generation run, to guarantee a clean slate.
Interview Question

How did you decide how much synthetic data to generate?

I didn't pick an arbitrary number. I ran a small test batch, measured the real class distribution of encounter types, and calculated that only ~4% of encounters (inpatient/emergency) qualify for my label. I sized the population so that rare-class volume would be large enough for the model to learn from — then cross-checked that against actual disk space, and adjusted the Synthea config to exclude fields I don't need, rather than just requesting fewer patients.

Error / Gotcha Old Java version silently shadowing a new install (PATH ordering)

Machine had Java 8; Synthea requires 11+. Installed Java 21 via winget, but java -version kept reporting 1.8.0 even after reopening the terminal once.

Root cause: an old Oracle Java 8 stub launcher (...\Common Files\Oracle\Java\javapath\java.exe) sat earlier in PATH than the new install. Fix: fully closing and reopening the terminal (not just clearing it) let Windows re-resolve PATH in the correct order — resolved without needing a manual JAVA_HOME override. This same "PATH doesn't refresh in an already-open shell" issue recurred with winget install Terraform and with VS Code's integrated terminal (which needed a full VS Code restart, not just a new terminal tab).
Interview Question

You installed a new tool version but the terminal still runs the old one. What's happening?

PATH is loaded into a shell's environment at the time it starts — it doesn't live-refresh from installer changes. The fix is to fully restart the shell (or, for an IDE's integrated terminal, the whole application) so it re-reads the system PATH. If it's still wrong after that, I'd check where.exe <tool> to see every install on PATH in resolution order, and fix ordering or set an explicit environment variable (e.g. JAVA_HOME) if an old version is shadowing the new one.

Decision AWS account security — root lockdown before any resources

Order of operations was deliberate: create account → enable MFA on root → set a billing alarm → create a scoped IAM user for daily work → log out of root entirely. No AWS resource was created before all four of these existed.

  • Root user MFA enabled (authenticator app)
  • Zero-spend budget alarm created (alerts above $0.01 — separate from the $100 free-credit pool, which it does NOT track)
  • IAM user carepulse-admin created with AdministratorAccess, MFA enabled
  • Region standardized on us-east-1 for the whole project
Why root gets locked away: root has unlimited, unrevocable-by-others power over the account. An IAM user's permissions can be revoked instantly by any other admin (or from another device) if compromised — root has no such safety valve. Same least-privilege principle used for the Spotify project's Cloud Function service accounts.

Gotcha: AWS's "Zero-Spend Budget" tracks billed cost, not free-tier credit consumption — it will stay silent while the $100 promotional credit is draining, since that shows as $0 charged. The credit balance itself must be checked manually on the dashboard; the alarm only becomes an active safety net once that credit hits zero.

Interview Question

Walk me through how you'd secure a brand-new AWS account before deploying anything.

Enable MFA on the root user immediately — root is the account owner with unlimited power and no one can revoke it if compromised. Set a billing/budget alarm before creating any resources, so unexpected cost is caught immediately rather than discovered on a bill. Create a separate IAM user (or role) with only the permissions actually needed, and use that for all day-to-day work — root should only be used for rare account-level tasks afterward. This mirrors least-privilege practice everywhere else: scope the blast radius of any single credential.

Concept Terraform — what it is, and why this role wants it

Terraform is declarative infrastructure-as-code: you describe the desired end state of infrastructure in .tf files, and Terraform diffs that against a state file recording what it previously created, then computes the minimum change needed.

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

Core workflow, always in this order:

CommandWhat it does
terraform initDownloads the provider plugin (once per project)
terraform planShows exactly what would change — nothing is touched yet
terraform applyMakes the change, after review
Why this vs. imperative scripts (e.g. a folder of aws cli commands): an imperative script has no idea what already exists — re-running it can duplicate resources or error out. Terraform's state file means it always knows current reality, so re-applying an unchanged config is a no-op. It's also cloud-agnostic (same tool/language for AWS, GCP, Snowflake, etc.), which is why it's the de facto standard across nearly every Senior/SWE III posting reviewed for this project — unlike CloudFormation, which is AWS-only.
Interview Question

What's the difference between declarative and imperative infrastructure management, and why does it matter?

Imperative means specifying the exact steps to reach a result — e.g. a script of CLI commands run in order. It has no memory of prior state, so re-running it can be unsafe or non-idempotent. Declarative (Terraform's model) means specifying the desired end state; the tool computes the diff against what actually exists (tracked in a state file) and applies only the necessary changes. This makes infrastructure changes reviewable before they happen (terraform plan), reproducible, and safe to re-run.

Interview Question — now answered, from firsthand build

Two engineers both run terraform apply on the same infrastructure at nearly the same time. What goes wrong, and how is it prevented?

With local state (a .tfstate file on someone's laptop), both engineers read state independently, compute a plan, and race to write the same state file when they finish — this can corrupt the file, or leave state reflecting only one apply even though both created real AWS resources, producing untracked infrastructure. The fix is a remote state backend with locking: state lives in a shared location (commonly S3), and before any apply runs, Terraform acquires a lock (via a DynamoDB table, in the classic pattern). A second apply attempted while the lock is held fails outright with a "state is locked" error, rather than racing — I built exactly this setup this session.

Decision Remote state: S3 backend + DynamoDB locking

Bootstrapped remote state using Terraform itself: created an S3 bucket (versioned, for rollback safety) to hold terraform.tfstate, and a DynamoDB table (PAY_PER_REQUEST billing) purely for lock records, keyed on LockID. Added a backend "s3" { ... } block to main.tf, re-ran terraform init, and confirmed the migration prompt before typing yes to copy local state into the new backend.

Chicken-and-egg note: the remote-state infrastructure itself had to be created using local state first — a one-time, standard exception to "always use remote state."

Deprecation noted, not acted on: the AWS provider (v5.100.0) warns that dynamodb_table is deprecated in favor of native S3 locking (use_lockfile). Deliberately kept the DynamoDB pattern for now — it's still the dominant pattern in existing company codebases, and understanding it matters more at this stage than being on the newest syntax.

Error / Gotcha IPv6 routing instability blocked HashiCorp + AWS traffic

terraform init repeatedly failed with wsarecv: An existing connection was forcibly closed by the remote host when downloading the AWS provider. Later, aws sts get-caller-identity and aws s3 ls began hanging indefinitely with no error at all.

Diagnosis, done in order rather than guessing:
TestResultRuled out
ping 8.8.8.812–15ms, 0% lossBasic internet connectivity
nslookup sts.amazonaws.comResolved cleanlyDNS resolution

$env:GODEBUG="netdns=go+ipv4"Fixed terraform init once, not consistently—

Every failing connection traced through the same IPv6 address prefix (2605:a601:af5c:ff00:...), including the DNS server itself. Consistent with IPv6 being technically live but unreliable for sustained HTTPS/TLS connections on this network — a known class of ISP/router IPv6 issue.

Resolution: a plain reboot fixed it completely — no IPv6 disable needed. Post-reboot, ping, aws sts get-caller-identity, and terraform init all worked instantly with no workarounds. Confirms it was transient adapter/routing state, not a persistent router/ISP-level break — worth trying the cheapest fix (reboot) before a system-level change (Disable-NetAdapterBinding), which stayed un-applied and wasn't needed.

Interview Question

You hit a network error during a cloud deployment. Walk me through how you'd debug it.

I isolate layer by layer rather than guessing: first confirm basic connectivity (ping a known IP, bypassing DNS entirely), then DNS resolution specifically (nslookup the failing hostname), then whether the failure is tool-specific or systemic (test the same class of call — an HTTPS/API request — with a different tool). In my case, ping and DNS both worked, but HTTPS calls hung across multiple unrelated tools (Terraform and the AWS CLI), which pointed at the connection/TLS layer rather than DNS or basic routing — and every failing address traced back to the same IPv6 prefix. I tried the lowest-risk fix first (a reboot, which resets adapter/DNS state) before reaching for a system-level change like disabling IPv6 on the adapter — and the reboot alone resolved it.

Error / Gotcha AWS Console showed "no tables" — wrong region selected

DynamoDB console showed Tables (0) and "You have no tables in this account in this AWS Region," even though terraform apply had just created carepulse-terraform-locks successfully.

Root cause: the console's region selector (top-right) was set to Ohio (us-east-2), while every resource in this project — set explicitly in the Terraform provider block — lives in N. Interview Question

What's the difference between S3 and DynamoDB — when would you use each?

S3 is object storage — it stores whole files (objects) and hands them back whole; it doesn't understand structure inside the file. DynamoDB is a NoSQL database — it stores structured records (items) with named fields and supports fast lookups/updates on individual records by key, with atomic conditional-write guarantees. I used S3 for the Synthea CSVs and the Terraform state file, because both are files read/written as a whole. I used DynamoDB purely for Terraform's lock records, because locking needs an atomic "is this currently held" check on a tiny record — something DynamoDB is built for and S3 traditionally wasn't (though S3 has since added native locking as an alternative). The general pattern: object storage for large, unstructured/whole-file data; NoSQL for fast structured lookups; a data warehouse like Snowflake when you need complex queries and joins across relationships.

Session 2 — Phase 1: S3 Event Validation (in progress)

Sep 2026

Decision What "validation" means, made concrete before writing code

Defined validation as three checks per file, based on columns actually inspected in the real uploaded data (not assumed from docs): required columns present, file non-empty, at least one real data row beyond the header. Built a standalone validate.py script — run locally against real S3 objects — to prove this logic before wrapping it as a deployed Lambda. Same discipline as the Spotify digest function: prove logic locally first, deploy second.

FileRequired columns (from real inspection)
patients.csvId, BIRTHDATE, GENDER
encounters.csvId, START, STOP, PATIENT, ENCOUNTERCLASS
conditions / medications / procedures.csvSTART, PATIENT, CODE, DESCRIPTION
observations.csvDATE, PATIENT, CODE, VALUE
Result: proved against real data. 6/6 real files ACCEPTED; a deliberately malformed test file correctly REJECTED with the exact missing columns named; an untracked filename correctly SKIPPED rather than false-flagged.

Concept boto3 — AWS's Python SDK

The AWS equivalent of google.cloud.storage / google.cloud.secretmanager from the Spotify project — a Python library that talks to AWS services directly, instead of shelling out to the aws CLI. One client object (boto3.client("s3")) covers every S3 operation used.

Two authentication paths, same as the CLI vs. Lambda distinction: running locally, boto3 automatically finds the carepulse-admin keys already configured via aws configure. Running inside an actual deployed Lambda, boto3 instead uses the function's execution role (an IAM role, not a long-lived access key) — safer, since a role has no static secret that can leak. This distinction matters when Phase 1 moves from local script to deployed function.

Technique S3 range reads — validating without downloading gigabytes

obj = s3.get_object(Bucket=BUCKET, Key=key, Range="bytes=0-8192")

The Range parameter asks S3 for only the first 8KB of an object, not the whole file — enough to get the header row and a few sample rows. Essential here: observations.csv alone is 7.7 GB, and validation should be cheap and fast, not require downloading the entire file just to check its column names.

Error / Gotcha BOM character caused a false "missing column" reading

A manually-created test CSV (via PowerShell's Out-File -Encoding utf8) produced a header that read as '\ufeffWRONG' instead of 'WRONG' when decoded — a hidden Byte Order Mark character silently prepended to the file.

Why it matters beyond this one test: if any real upstream file ever had a BOM, the first column name would never exactly match the rulebook (e.g. '\ufeffId' ≠ 'Id'), causing a false rejection of genuinely good data — arguably worse than a false acceptance, since it silently blocks correct data for a reason that looks legitimate.

Verified before "fixing": checked the real Synthea encounters.csv directly — no BOM present, confirmed via repr(header[0]) printing clean 'Id'. So this wasn't an active bug, but the fix (decode with "utf-8-sig" instead of "utf-8") was applied anyway as free defensive insurance — one word changed, zero downside, protects against any future upstream source that does add a BOM.

Interview Question

How would you validate a large file lands correctly in S3 without downloading the whole thing?

Use an HTTP Range request via get_object(..., Range="bytes=0-N") to pull only the first few KB — enough to parse a header row and a handful of sample rows for a CSV, or check a magic-byte signature for a binary format. This keeps validation cheap and fast even for multi-gigabyte files, and is the same underlying mechanism video streaming and resumable downloads use to fetch partial content.

Technique Tracing execution value-by-value to build real understanding

When the flow of values through fetch_header_and_sample → validate_file wasn't clicking from reading the code alone, wrote a parallel trace.py with a print statement after every single transformation — raw bytes → decoded text → split lines → parsed CSV rows → header list → header set → the set-subtraction result — and ran it against one real call (validate_file("encounters.csv")).

Why this works better than re-reading code: reading code and tracing execution are different skills. Seeing the actual intermediate values for one real, concrete call — not an imagined generic case — turns "I copy-pasted working code" into genuine understanding of what each line does and why. A reusable debugging habit, not a one-off: add throwaway print statements, trace one real example fully, remove them once the shape is clear.

Reference validate.py — full code, explained chunk by chunk

The complete file as it stands at the end of this phase, with every function's purpose and every non-obvious Python/boto3 feature called out. Kept here as the canonical reference to re-read before explaining this project in an interview.

import boto3
import csv
import io

s3 = boto3.client("s3")
BUCKET = "carepulse-raw-preetham-2026"

EXPECTED_COLUMNS = {
    "patients.csv":    {"Id", "BIRTHDATE", "GENDER"},
    "encounters.csv":  {"Id", "START", "STOP", "PATIENT", "ENCOUNTERCLASS"},
    "conditions.csv":  {"START", "PATIENT", "CODE", "DESCRIPTION"},
    "medications.csv": {"START", "PATIENT", "CODE", "DESCRIPTION"},
    "procedures.csv":  {"START", "PATIENT", "CODE", "DESCRIPTION"},
    "observations.csv":{"DATE", "PATIENT", "CODE", "VALUE"},
}

def fetch_header_and_sample(key, sample_rows=5):
    obj = s3.get_object(Bucket=BUCKET, Key=key, Range="bytes=0-8192")
    text = obj["Body"].read().decode("utf-8-sig", errors="replace")
    lines = text.splitlines()
    reader = csv.reader(lines)
    rows = list(reader)
    return rows[0] if rows else [], rows[1:sample_rows+1]

def validate_file(key):
    if key not in EXPECTED_COLUMNS:
        return {"key": key, "status": "SKIPPED", "reason": "not a tracked file"}
    try:
        header, sample = fetch_header_and_sample(key)
    except Exception as e:
        return {"key": key, "status": "REJECTED", "reason": f"could not read: {e}"}
    if not header:
        return {"key": key, "status": "REJECTED", "reason": "empty file, no header"}
    header_set = set(header)
    required = EXPECTED_COLUMNS[key]
    missing = required - header_set
    if missing:
        return {"key": key, "status": "REJECTED", "reason": f"missing columns: {missing}"}
    if not sample:
        return {"key": key, "status": "REJECTED", "reason": "header present but no data rows"}
    return {"key": key, "status": "ACCEPTED", "reason": f"{len(header)} columns, sample OK"}

def quarantine_file(key, reason):
    copy_source = {"Bucket": BUCKET, "Key": key}
    dest_key = f"quarantine/{key}"
    s3.copy_object(Bucket=BUCKET, CopySource=copy_source, Key=dest_key)
    s3.delete_object(Bucket=BUCKET, Key=key)
    print(f"  -> moved to {dest_key} (reason: {reason})")

def lambda_handler(event, context):
    results = []
    for record in event["Records"]:
        key = record["s3"]["object"]["key"]
        result = validate_file(key)
        results.append(result)
        print(f"{result['status']:10} {result['key']:20} {result.get('reason','')}")
        if result["status"] == "REJECTED":
            quarantine_file(key, result["reason"])
    return {"results": results}

if __name__ == "__main__":
    fake_event = {
        "Records": [
            {"s3": {"bucket": {"name": "carepulse-raw-preetham-2026"}, "object": {"key": "encounters.csv"}}}
        ]
    }
    output = lambda_handler(fake_event, None)
    print(output)

Decision / Gotcha The quarantine re-trigger loop risk — caught before it happened

S3 event notifications can only include by prefix/suffix filter — there's no native way to exclude a prefix. Wiring the trigger to the whole bucket meant a file written to quarantine/ by quarantine_file() would itself fire the Lambda again.

The fix — explicit, not incidental: the code already avoided a real loop by accident (quarantine/encounters.csv isn't a key in EXPECTED_COLUMNS, so it would fall through to SKIPPED) — but relying on an implicit side-effect of a dict lookup is fragile and non-obvious to a future reader. Added an explicit guard as the very first check in lambda_handler:
if key.startswith("quarantine/"):
    print(f"SKIPPED    {key:20} (quarantine write, ignored to avoid re-trigger loop)")
    continue

Tested locally first (fake event with a quarantine/ key → confirmed {'results': []}, meaning the file was never even read from S3, not just quarantined again) — then re-zipped, re-deployed via terraform apply (a code-only update: source_code_hash changed, IAM role/policy untouched), and the fix shipped before the trigger was ever wired up live.

Interview Question

You're wiring an S3 event to a Lambda that also writes back to the same bucket. What's the risk, and how do you prevent it?

S3 notifications can filter by prefix/suffix to include certain keys, but there's no native filter to exclude one — so if the Lambda's own output lands in the same bucket (like a quarantine or processed-output folder), that write can itself trigger the function again. I handle it with an explicit early-exit guard in the handler — checking the key against the output prefix before any real work happens — rather than relying on downstream logic to incidentally ignore it. Explicit guards are safer than incidental ones because they document the risk for the next person reading the code, and they don't silently break if the downstream logic ever changes.

Coding Practice SQL — "gaps and islands" (longest consecutive-login streak)

Given a table of one row per user per login date, find each user's longest run of consecutive calendar-day logins. First attempt used PARTITION BY user_id, login_date with ORDER BY COUNT(*) DESC inside a window function — invalid syntax, and conceptually wrong (that partition puts every row alone in its own group, since a user never logs in twice on the same date).

Second attempt correctly identified the real trick but used an unsupported INTERVAL '1' DAY * ROW_NUMBER() multiplication.

WITH ranked AS (
  SELECT user_id, login_date,
         login_date - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS grp
  FROM user_logins
),
streaks AS (
  SELECT user_id, grp, COUNT(*) AS streak_length
  FROM ranked
  GROUP BY user_id, grp
)
SELECT user_id, MAX(streak_length) AS longest_streak
FROM streaks
GROUP BY user_id;
The core insight: subtracting a sequential row number from a sequential date produces a constant value for every row in an unbroken consecutive run — because both the date and the row number climb by exactly 1 together, the difference stays frozen. The instant there's a gap, the difference jumps to a new constant. That computed value becomes a free grouping key for each unbroken "island" of consecutive dates. Fix for the syntax error: plain integer subtraction on a date (login_date - ROW_NUMBER() OVER (...)) works directly in Snowflake — no INTERVAL needed at all.

Interview-floor move worth remembering: state the relied-on assumption out loud even when the problem guarantees it — "I'm assuming no duplicate same-day logins, since ROW_NUMBER() would silently corrupt the grouping key otherwise."

Interview Question

How would you find the longest streak of consecutive-day activity per user in SQL?

This is the classic "gaps and islands" pattern. Subtract a per-user sequential row number (ordered by date) from the date itself — for any unbroken run of consecutive dates, that difference stays constant, and it changes the moment there's a gap. Group by that computed value to isolate each streak, count the rows in each group to get streak lengths, then take the max per user. The same subtract-a-counter trick generalizes to any "find consecutive runs" problem, not just dates.

Gotcha 9 output files from a source file thought to be 3.6MB

First run of transform_encounter.py (a bare spark.read.csv(...).write.parquet(...), deliberately unoptimized) produced 9 separate part-*.snappy.parquet files, each ~21MB.

Gotcha Concurrent job runs colliding on the same output path

Started a second start-job-run while the first was still RUNNING, both targeting the identical curated/encounters/ output path. The second run failed: Failed to delete key: curated/encounters.

Why: Spark's mode("overwrite") deletes existing files at the target path before writing new ones. Two concurrent jobs performing that delete-then-write cycle against the same prefix can collide — no file-locking exists in S3 to prevent it. Same category of problem as the Terraform state race condition from Phase 0, different layer of the stack. Rule going forward: never start a second run of a job targeting the same output while an earlier run is still in flight — wait for SUCCEEDED/FAILED first.

Gotcha The real root cause — found by not trusting an initial theory

The exact same Failed to delete key: curated/encounters error recurred on a later, non-concurrent run — disproving the concurrent-write theory as the sole explanation, since nothing else was running that time.

Actual root cause: the Glue IAM policy granted GetObject, PutObject, and ListBucket — but never DeleteObject. The very first run succeeded only because the output path was empty (nothing to delete, so the missing permission was never exercised). Every run after that had real files to overwrite, which requires DeleteObject — and failed. Fix: add "s3:DeleteObject" to the policy's action list, terraform plan (showed a clean in-place update, not a new resource) and apply.

The methodology point, not just the fix: when a repeat failure doesn't fit the first theory, the theory needs to be dropped, not defended — the concurrent-write explanation was a reasonable first guess, but the second failure (under different conditions) was evidence that should override it, not be explained away.

Interview Question

You've deployed a Glue job with what looks like the right IAM permissions, and it works the first time — then fails on every run after that. How do you debug it?

I don't trust that "worked once" means the permissions are correct — I check what's actually different between the successful run and the failing ones. In my case, the first run wrote to an empty S3 prefix, and every later run needed to overwrite existing files first. That's the clue: overwrite mode deletes before it writes, so a permission set that's missing DeleteObject looks completely fine until there's something to delete. The fix is reading the actual IAM policy against the actual operation being attempted, not assuming a first success proves the whole permission set is right.
